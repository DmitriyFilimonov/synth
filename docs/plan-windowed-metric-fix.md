# План: непрерывное оконное покрытие метрики suppression

Документ-задание для реализации (Qwen). Цель — устранить скачки
метрики `evaluateSuppressionWindowed` на границах кратности 100 мс.

## Проблема

`evaluateSuppressionWindowed` (`src/optimize/evaluate.ts`) делит
сигнал на окна по 100 мс (`WINDOW_SIZE_SECONDS = 0.1`):

```ts
const windowCount = Math.max(1, Math.floor(length / windowSize));
const step = Math.floor(length / windowCount);
```

Последствия:

1. **Дискретный скачок числа окон.** При длине сигнала 199 мс —
   1 окно, при 200 мс — 2 окна. Средний по-оконный score меняется
   скачком при пересечении границы, хотя сигнал почти не изменился.
2. **Хвост короче окна игнорируется.** При 130 мс окно одно
   (0–100 мс), последние 30 мс не участвуют в `avgLocalScore`
   (участвуют только в глобальном score через `shapePenalty`).
3. **Влияние на staged-оптимизацию.** Стадии растут (10 → 20 → 30 →
   120 → … мс), и на переходах через кратность 100 мс метрика
   несопоставима между стадиями: часть входных «падений» score при
   смене стадии — артефакт метрики, а не реальная деградация.

## Требуемое решение

Переработать разбиение на окна так, чтобы покрытие было
непрерывным, а метрика — гладкой по длине сигнала:

1. **Покрывать весь сигнал.** Последнее окно должно включать хвост:
   либо неполное окно с весом, пропорциональным длине
   (`weight = count / windowSize`), либо последнее окно прижимается
   к концу сигнала (`start = length - windowSize`, допускается
   перекрытие с предпоследним).
2. **Взвешенное среднее.** `avgLocalScore` считать как
   `Σ(score_i · weight_i) / Σ(weight_i)`, где `weight_i` — доля
   длины окна (полное окно = 1). Это убирает скачок при появлении
   нового окна: новое короткое окно входит с малым весом и растёт
   плавно.
3. **Сохранить фильтр тишины.** Окна с `targetRMS < 1` по-прежнему
   пропускаются (не входят ни в сумму, ни в веса).
4. **Fallback без изменений.** Если ни одно окно не использовано —
   текущий fallback на глобальный `assessCancellationQuality`.

## Ограничения и инварианты (НЕ нарушать)

- Сигнатура `evaluateSuppressionWindowed(generated, targetSignal,
  penaltyWeight, spectralWeight, sampleRate)` — не менять
  (вызывается из `coordinate-descent.ts`, `staged.ts`).
- Код синхронный, без внешних зависимостей (работает в
  `worker_threads`).
- Не увеличивать существенно стоимость вызова: функция стоит на
  горячем пути (тысячи вызовов за итерацию CD). Число вызовов
  `findOptimalScaleFor` должно остаться ~тем же (число окон
  не должно вырасти более чем на 1).
- Формула итога сохраняется:
  `avg·(1−spectralWeight) + spectral·spectralWeight − penalty·shapePenalty`.

## Обязательная A/B-проверка

Изменение метрики глобально влияет на оптимизатор — без A/B не
мержить:

1. Собрать: `npm run prettier && npm run build`.
2. Взять 2–3 референсных WAV (например, сгенерировать из пресетов
   `src/presets.ts` через `npm run dev`).
3. Прогнать match (staged, дефолтные параметры) на old/new метрике
   с одинаковым seed-инициализатором; сравнить финальный
   `suppressionPercent` (RMS-based, из `cancellation-assessment.ts` —
   она не меняется и служит арбитром).
4. Критерий: новый вариант не хуже старого более чем на 1 п.п.
   на каждом файле; скачки метрики на границах 100/200/300 мс
   исчезли (проверить unit-скриптом: score(len=199ms) ≈
   score(len=200ms) для одного и того же сигнала, дельта < 0.5 п.п.).
5. После правок `src/optimize/` запустить субагента
   `optimizer-reviewer`.
