# План: ускорение первых циклов оптимизации (EXPLORATION / REFINEMENT)

Документ-задание. Контекст: A/B трёхскоростного шага частоты
(коммиты `5c58534`, `12840e1`) показал, что одна итерация CD на
полном сигнале 500 мс / 12 осцилляторов стоит ~55 с, а прогон на
200 итераций — ~3 часа. Основные затраты — в первых двух циклах
(140 из 200 итераций при долях бюджета 35/35/30).

## Измеренная стоимость оценки (12 осц., сигнал 500 мс)

| Длина оценки | Синтез | Windowed-eval | Итого/оценка |
| ------------ | ------ | ------------- | ------------ |
| 500 мс       | 110 мс | 331 мс        | ~440 мс      |
| 300 мс       | 42 мс  | 206 мс        | ~248 мс      |
| 200 мс       | 30 мс  | 129 мс        | ~159 мс      |
| 100 мс       | 15 мс  | 64 мс         | ~79 мс       |

Итерация ≈ 216 кандидат-оценок (12 осц. × 9 параметров × 2 стороны),
стоимость почти линейно падает с длиной сигнала.

## Идея (обсуждаемая, НЕ утверждённая)

В flat-режиме оценивать EXPLORATION/REFINEMENT на превью сигнала
(первые ~200–300 мс или подвыборка окон), а PRECISION — на полном
сигнале. Ожидание: 140 ранних итераций дешевеют в ~2.5–3 раза,
прогон ~3 ч → ~1.5–1.7 ч.

## Проблемы идеи и их решения

### П1. Оптимум превью ≠ оптимум полного сигнала (сдвиг ландшафта)

Ранние циклы подгонят параметры под оптимум «головы» сигнала; для
нестационарных сигналов (затухания, поздние партиалы, дрейф частоты)
PRECISION получит старт, который придётся переезжать, тратя
гарантированные итерации на коррекцию вместо финишной шлифовки;
возможно застревание в локальном минимуме «головы».

Решения:
- (а) Превью = равномерная подвыборка окон (полный сигнал = 5 окон
  по 100 мс; оставить окна 0/200/400 мс): покрытие времени полное,
  стоимость ~0.6× вместо 0.36×, оптимум почти совпадает с полным.
- (б) Превью только для EXPLORATION; REFINEMENT — на полном сигнале.
- (в) Детекция нестационарности (сравнение спектра головы и хвоста,
  Goertzel на паре частот): если сигнал меняется — превью не
  использовать.

### П2. Потеря точности на стыке циклов

REFINEMENT должен передать PRECISION частоты в окрестности, из
которой шаг 0.002 Гц дойдёт до оптимума за бюджет. На коротком
превью (усреднение по 2 окнам) ландшафт площе, шаг 0.1 Гц даёт
меньший различимый прирост → ложная стогнация и ранний выход по
minStep → PRECISION стартует с ошибки ±1 Гц при бюджете ходьбы
~0.1–0.2 Гц.

Решения:
- Для превью-циклов отключить выход по minStep (только по cap).
- Поднять `stagnationExitThreshold` в превью-циклах (4 → 8).
- Либо превью только для EXPLORATION (стык REF→PREC не страдает).

### П3. Единообразие метрики внутри цикла

Метрика вызывается на полном сигнале из многих мест (шаги, кики,
прунинг, scale fitting, финальная оценка). Превью-режим вводит
состояние «длина оценки зависит от цикла»; разная длина внутри
одного цикла (кик на полном, шаг на превью) ломает сравнение score.

Решения:
- Превью — явный параметр конфига CD (`evaluateSamples?: number[]` —
  набор окон с весами), применяемый единообразно ко всем оценкам
  цикла, с логом `[CoordDescent]`. Инвариант: все оценки одного
  цикла — на одной метрике.

### П4. Дублирование staged-механизма

Staged-режим (`staged: true`) уже реализует нарастающие стадии
10 → … → 500 мс с оценкой на коротких кусках головы сигнала.
Превью-идея в flat-режиме — его локальная имитация без HPO.

Решения:
- Сначала измерить flat+превью против готового `staged: true` —
  возможно, staged уже даёт нужное без новых правок.

### П5. Преждевременность оптимизации

Выигрыш ~1–1.3 ч на прогон при неизвестном «потолке» A/B. Если оба
конфига выходят на одно плато, ускорение ранних циклов не поможет
финалу. Новая ветка поведения потребует повторного A/B
(2–3 пары по ~2 ч).

## Порядок работ

1. Дождаться завершения текущего A/B (NEW vs OLD, 12 осц. / 200 итер,
   Untitled.wav) — вердикт «работает ли трёхскоростной шаг».
2. Если прирост подтверждён: реализовать по приоритету:
   - (б) превью только для EXPLORATION, подвыборка окон
     (0/200/400 мс), выход по cap без minStep;
   - замер ускорения и качества (A/B против текущего);
   - (в) решить, нужен ли превью для REFINEMENT, сравнив с
     `staged: true`.
3. Не трогать код во время текущих прогонов — сравнение ломается.

## Ограничения (НЕ нарушать)

- Публичные инварианты оптимизатора: `ArgOptimize`, `ProgressCallback`,
  возврат `{ vector, history }`, значения вектора в `[0,1]`, `on` ∈
  {0,1} (см. AGENTS.md).
- `evaluateSuppressionWindowed` сигнатуру не менять; любые превью-
  правки — в CD-конфиге, не в метрике.
- Код синхронный, без внешних зависимостей (worker_threads).
