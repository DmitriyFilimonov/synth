# Спецификация контрактов сервиса улучшения бочек

Документ фиксирует форматы данных между стадиями сервиса, чтобы
майнинг (T7), улучшение (T9) и эндпоинт (T10) разрабатывались
независимо. План и мотивация — в `docs/plan-kick-enhancement.md`;
здесь только контракты. Все форматы версионируются полем `version`
и пересобираются одной командой из датасета (переобучение на новом
наборе не требует правок кода).

## C1. Карта идентифицируемости (`identifiability.json`)

Кто пишет: анализ стабильности (T6) по датасету прогонов.
Кто читает: улучшение (T9) — решает, что анкерить, а что отдать
модели.

```json
{
  "version": 1,
  "dataset": "reference-4",
  "createdAt": "2026-11-19T00:00:00.000Z",
  "params": {
    "freqBase": {
      "verdict": "anchored",
      "withinSeedMedianDelta": 0.008,
      "note": "медиана Δlog между сидами"
    },
    "phase": { "verdict": "free" },
    "endLevel": { "verdict": "prior-owned" }
  }
}
```

Словарь вердиктов:

- `anchored` — параметр стабильно восстанавливается из сигнала;
  это характер оригинала, улучшение его не трогает (или двигает в
  пределах trust region в режиме B).
- `free` — сигнал параметр не определяет (гуляет между сидами);
  значение заполняется из приоров.
- `prior-owned` — параметр залипает на значении init
  (init-артефакт, тест дрейфа); сигналу он не принадлежит,
  владелец — модель.
- `unknown` — данных мало (один сид, один таргет); безопасный
  дефолт — вести себя как `anchored`.

Карта пишется по классам параметров (`freqBase`, `freqStart`,
огибающие, фаза, уровни), при необходимости — раздельно по ролям
(`sustain`/`transient`), когда данных хватит.

Анкеринг работает на уровне признаков и кластеров, а не слотов:
первый разбор (BOg, 4 сида) показал, что спектральная структура
воспроизводится, а распределение компонентов по слотам гуляет
(по-слотовый разброс Δlog freqBase 0.174 против 0.008 у
сопоставленных пар). «Анкерить параметр» значит: держать его
признак внутри диапазона, который дал оригинал, независимо от
того, какому слоту он достался.

## C2. Приоры (`priors.json`)

Кто пишет: майнинг закономерностей (T7) по очищенным признакам
датасета. Кто читает: улучшение (T9), при режиме B — проекция на
семейство.

```json
{
  "version": 1,
  "createdFrom": {
    "dataset": "reference-4",
    "codeRevision": "git sha"
  },
  "families": [
    {
      "id": "sub-heavy",
      "roles": {
        "sustain": {
          "freqBaseHz": { "median": 50, "p10": 45, "p90": 60 },
          "freqStartToBase": { "median": 4.0, "p10": 3.8, "p90": 4.2 },
          "decayDb20Sec": { "median": 0.18, "p10": 0.15, "p90": 0.22 }
        },
        "transient": {}
      },
      "relations": [
        {
          "kind": "ratio",
          "name": "freqStart ≈ k·freqBase",
          "k": { "median": 4.0, "p10": 3.8, "p90": 4.2 }
        }
      ]
    }
  ]
}
```

Правила:

- Приоры хранят распределения (медиана + квантили), а не точечные
  значения: улучшение выбирает внутри диапазона, не копирует число.
- Семейства не зашиты в код: их состав и имена рождаются из
  кластеризации датасета, файл пересобирается.
- Отношения (`relations`) — проверенные вмешательством правила
  (этап 3 плана), не сырые корреляции.

## C3. Трансформации патча (`src/enhance/transforms.ts`)

Чистые функции `patch → { patch, audit | null }`. `audit = null`
означает «неприменимо, вход не тронут». Аудит человекочитаем и
складывается в артефакты job'а: сервис обязан уметь объяснить,
что он сделал с патчем. Вход никогда не мутируется; параметры
clamp'ятся в нормали; `endLevel` — относительный множитель.

## C4. Улучшение (T9)

Вход: стартовый патч (из match), карта идентифицируемости,
приоры, `enhancementStrength` (0..1, дефолт 0.5), опционально
принудительное семейство. Выход: улучшенный патч + массив аудита.

Режим A (достраивание): `anchored`-параметры не трогаем;
`free` и `prior-owned` заполняем из приоров семейства; сила
управляет тем, насколько далеко от текущего значения к приору
(0 — не менять, 1 — полностью приор).

Режим B (коррекция): `anchored`-параметры противоречат приору
семейства; двигаем их к приору в пределах trust region,
масштабированного силой. Расстояние считаем по перцептивно
значимым признакам (log-частоты, времена спада), не по сырым
параметрам — они неидентифицируемы (первые данные BOg это
подтверждают). Субмиллисекундная огибающая считается импульсом:
режим B не продлевает её до семейной длительности, потому что это
меняет импульс в громкий тон и ломает баланс атаки.

После трансформаций — опциональная короткая доводка CD (бюджет
порядка 20 итераций) с анкерингом; нужность и бюджет решаем по
этапу 4. Конкурирующий вариант без доводки (чистая хирургия)
проверяется тем же этапом. Реализованная C4 с анкерами прошла
слепой пилот с отрицательным результатом: она остаётся выключенной
и не считается улучшением.

## C5. Эндпоинт (T10)

`POST /api/enhance/job` (асинхронный job по правилам проекта):
вход — WAV; параметры — `enhancementStrength`, `seed`,
опционально `targetFamily`. Стадии job'а: match, карта
идентифицируемости, улучшение, опциональная доводка, синтез.
Артефакты job'а: патч и WAV стартового match, патч и WAV
улучшенного, журнал аудита трансформаций, `globalSuppressionPercent`
к исходному WAV (справочно, не как цель). UI — отдельной фичей
по FSD после стабилизации API.

## Смена контрактов

Любая правка схем C1–C5 поднимает `version` и отражается в этом
документе тем же коммитом. Читатели обязаны переживать отсутствие
необязательных полей (форвард-совместимость); писатели не удаляют
поля без подъёма мажорной версии.
