## Цель проекта и критерии достижения

Приоритетное направление — реверс-синтез: по эталонному WAV-файлу
подобрать конфигурацию осцилляторов аддитивного синтезатора проекта,
максимизирующую RMS-based suppressionPercent. Генерация по пресету —
вспомогательная функция, не приоритет.

### Два обязательных условия завершения

Проект решает две равнозначные задачи и завершён только тогда, когда
выполнены обе:

1. **Реверс-синтез** достигает целевого suppression не ниже 98% и не
   деградирует существующий путь мэтчинга.
2. **Сервис улучшает сырые и плохие записи басового барабана** по закону,
   проверенному на отложенных таргетах и вмешательством. Такой сервис
   проходит Q1–Q5, меняет структуру низа, когда это требует закон, и
   сохраняет характер оригинала.

Высокий suppression сам по себе не доказывает качество улучшения, а
субъективно улучшенная бочка не отменяет критерий реверс-синтеза.

### Артефакты каждого запуска реверс-синтеза

1. **JSON параметров для синтезатора** — главный (приоритетный)
   артефакт: конфигурация осцилляторов в формате `ArgCreateSynth`
   (как пресеты в `src/presets.ts`), пригодная для повторного синтеза
   без конвертации.
2. **WAV, синтезированный по подобранным параметрам** — обязателен,
   возвращается как и сейчас: пользователю нужна быстрая субъективная
   оценка результата.
3. Метаданные запуска: `suppressionPercent` (surrogate J),
   `globalSuppressionPercent` (честный глобальный suppression финального
   WAV по `assessCancellationQuality`; `null`, если оценка не удалась),
   история прогресса, `targetInfo`.

HTTP-job хранит метаданные в своём JSON. Прямой CLI пишет чистый патч
в `<wav>.params.json`, а метаданные и лучший вектор — в
`<wav>.metadata.json`. В датасете они находятся в `run.json`.

### Автоинициализация («без ручного ввода параметров»)

Стартовая конфигурация осцилляторов (частоты, фазы, амплитуды)
формируется автоматически из анализа сигнала (dual-window Goertzel /
simple-init-vector). Пользователь задаёт только параметры прогона
(`maxIterations`, `numOscillators` и т.п.), но не начальные
значения осцилляторов.

### Целевая метрика

- Цель: `suppressionPercent ≥ 98%` (порог совпадает с early-exit
  coordinate descent).
- 100% (посэмпловое совпадение) — идеал, но маловероятен и не является
  обязательным критерием.
- Текущее состояние: `reference-integral` завершён 32/32; global исходных
  match лежит в диапазоне 70.81–93.62%. Offline onset до 400 мс поднял
  лучший BOg до 84.25% и дал средний прирост +7.354 п.п. на четырёх сидах,
  но не помог GrumU. Историческое плато ~50% на single-scale и ~63% на однооконном
  описано в `README.md`. Это промежуточное состояние, а не цель: изменения
  не должны его деградировать, приоритет — приближение к 98%.
- **J больше не занижен систематически относительно честного global.**
  После перехода на энерго-взвешенное усреднение окон (см. «Multi-scale
  windowed-метрика») прежний хронический разрыв исчез: на части таргетов
  J и `globalSuppressionPercent` сходятся в пределах ~0.1 п.п. Прежнее
  расхождение было артефактом невзвешенного усреднения, а не свойством
  surrogate'а.
  **Но совпадение не гарантировано и не является инвариантом.** Величины
  агрегируются по-разному: global — одно отношение RMS по всему буферу,
  J — взвешенное среднее пооконных отношений. Они расходятся тем сильнее,
  чем неравномернее качество подгонки по окнам. Замеренный пример
  (`Mark Bester`, 300 итераций): J = 89.65%, global = 86.29% — разрыв
  3.4 п.п. на полностью исправном прогоне. Поэтому разрыв сам по себе
  **не** признак регрессии метрики; это признак неравномерной подгонки.
  Для оценки результата опирайся на `globalSuppressionPercent`.

### Второе направление: качественная бочка (закон качества)

Цель сервиса улучшения задаёт пользователь: бочка должна соответствовать закону, который определяет, что такое качественная бочка. Спектральный баланс, например вес низа, сам по себе критерием не служит: он годится только как следствие закона. Закон выводим из эталонов датасета, проверяем на отложенных таргетах и вмешательством, и только проверенный закон становится целью улучшения. Последовательности множителей, привязанные к фундаментальной частоте, законом не считаются, пока не доказана их инвариантность к высоте (T17 в `docs/plan-kick-enhancement.md`).

Структура низкочастотного тела приоритетнее его громкости и
длительности (решение пользователя, 2026-11-22). Сервис должен
уметь менять состав и связи компонентов, а не только усиливать их
или продлевать хвост. Основные частоты тела сохраняем по умолчанию.
Правку тела нельзя автоматически переносить на весь транзиент:
часть параметров атаки может сохраняться при смене высоты, часть
меняется вместе с натяжением мембраны, а смена конфигурации барабана
может изменить всё. Это гипотеза для T35, а не установленный закон.

Новых записей одной бочки на разных высотах не запрашиваем. Проект
сам строит конкурирующие высотные варианты из существующих патчей
и заранее фиксирует неизменные параметры. Синтетика проверяет только
механику оператора; закон подтверждают реальные отложенные таргеты,
структурные порчи и слух. Подробности — в разделе «Приоритет
структуры» и T35 в `docs/plan-kick-enhancement.md`.

Критерии (пороги фиксируются при первом проходе закона и согласуются с пользователем):

- **Q1. Закон определён.** Отношения закона проверены на отложенных таргетах (закон строится без таргета, на котором мерим) и вмешательством. Отчёт лежит в каталоге датасета.
- **Q2. Закон разделяет.** Оценка закона у эталонов выше, чем у порченых копий тех же эталонов. Доля разделённых порч не ниже порога, согласованного при фиксации закона.
- **Q3. Улучшение ведёт к закону.** Оценка закона у улучшенного патча выше, чем у исходного, на отложенных плохих бочках. На эталонах регрессии нет.
- **Q4. Характер сохранён.** Идентифицированные признаки оригинала (f0, спад −20 дБ, баланс полос) остаются в допуске. Допуск берём по разбросу сидов.
- **Q5. Слух.** Слепое прослушивание предпочитает улучшенный вариант. Среднее берём по не менее чем четырём сидам.

Критерий реверс-синтеза (suppression ≥ 98 %, путь мэтчинга) не меняется и не должен деградировать.

Восемь эталонов и повторные сиды достаточны для поиска структуры конкретного
WAV и screening-проверок, но не доказывают общий закон качества. Сиды не
считаются независимыми звуками. После многократного выбора гипотез на одном
наборе leave-one-target-out не заменяет полностью новый holdout. Предварительные
Q1–Q5 допустимы, но сильный кандидат требует явного разговора о финальной
валидации на независимых реальных бочках; исследование при этом не останавливаем.
Подробности — в разделе «Достаточность датасета» плана.

### Прогресс в чате (живой вывод команд)

opencode показывает вывод bash-команд в чате сессии вживую: чанки
stdout доставляются в карточку tool-вызова по мере поступления
(streaming metadata), пока команда выполняется. Чтобы прогресс
длинных операций (бенчи, оптимизация, подбор параметров) был виден
в чате:

- **НЕ используй `| tail` и `| head` для длинных команд** — они
  отдают строки только после завершения команды: в чате нет ничего,
  пока команда не закончится.
- Фильтруй построчно: `grep --line-buffered -E '...'` (или
  `stdbuf -oL ...`) — каждая подходящая строка сразу уходит в чат.
  Без `--line-buffered` grep буферизует вывод в пайп.
- Если нужен только итог — выведи его отдельной строкой/командой
  в конце, а не хвостом через `tail`.
- Для команд дольше ~1-2 минут задавай явный `timeout` (мс):
  дефолт bash-инструмента — 2 минуты, команда будет убита
  по таймауту.
- Скрипты и бенчи печатай построчно (`console.log`), не перезаписывай
  одну строку через `\r` — в чате останется только последнее
  состояние.
- В TUI карточку tool-вызова можно развернуть командой `/details`.

Пример правильного запуска бенча (виден живой прогресс итераций):

```bash
npx tsx /tmp/opencode/bench-full.ts 2>&1 | \
  grep --line-buffered -E 'RESULT|Iteration|Random restart|Post-pruning|After scale'
```

## Архитектура

Проект — генератор-синтезатор. Создаёт файл `.wav` (44 100 Гц, 16 бит,
моно) путём аддитивного синтеза до 50 осцилляторов. Включает пайплайн
подбора параметров: оптимизатор находит конфигурацию осцилляторов,
воспроизводящую заданный WAV-файл, максимизируя RMS-based
cancellation % (suppressionPercent).

FFT не используется в рантайм-синтезе. Использование спектрального
анализа для инициализации или метрики оптимизатора — допустимо.

Оптимизация выполняется в worker-потоке (`optimizer-worker.ts`),
API поддерживает асинхронный режим через job-очередь.

### Пайплайн подбора параметров

```
External WAV → Parse samples → Init vector →
Optimize (coordinate descent, worker thread) →
Generate → Compare → Save WAV + SVG
```

Сравнение возвращает центы и секунды. Это измерения, а не готовые допуски по сидам |

| `src/dual-window-init-vector.ts` | **Основной init** (используется в `match.ts` и API `synth-service.ts`). Двухоконный Goertzel-анализ: (1) sustain-скан всего сигнала 20–5000 Гц с разрешением 2 Гц — детектит длящиеся гармоники, получают `ampDur = effectiveDuration` (по 5%-хвосту RMS), `slope=0.8`; (2) transient-скан первых ~20 мс 200–15000 Гц с разрешением 50 Гц — детектит attack-транзиент, получают `ampDur = 40ms`, `slope=2.0` (быстрое затухание). Бюджет 60/40 sustain/transient, слоты мигрируют. Peak-фильтрация по разделению (sustain 8 Гц, transient 100 Гц) и порогу шума (2% от макс. амплитуды). Amplitude calibration через глобальный scale: суммарный RMS осцилляторов ≈ RMS таргета. Init-only global suppression 3–5% (положительный на всех реальных таргетах — vs simple/fft, которые дают −0.5..−27%)|
| `src/simple-init-vector.ts`      | Legacy init: Goertzel + STFT-гармоники. Beats-ветка не доверяет «пикам» тихой четверти (RMS < max(8 int16, 2% громкой четверти) → fallback на пики другой четверти без chirp); диапазон поиска 20–1860 Гц; амплитуды по энергии таргета (без завышения); ampEnv duration — по эффективной длительности сигнала (огибающая < 5% пика), а не на весь буфер. Заменён `dualWindowInitVector` в основном пайплайне |
| `src/fft-init-vector.ts`         | Legacy init: FFT на коротком окне (~23ms). ### Оптимизатор (src/optimize/)

#### Раскладка вектора

50 осцилляторов × 10 параметров (`OSC_PARAMS = 10`).
Смещение `[0]` каждого осциллятора — флаг on/off, `[1..9]` —
непрерывные параметры. Имена и позиции задаёт
`src/vector-param-offsets.ts`; денормализация остаётся в
`src/vector-to-synth-config.ts`.

#### Инварианты (НЕ нарушать)

- Сигнатуры `ArgOptimize`, `ProgressCallback` и возврат
  `{ vector, history }` — публичный контракт (используются в
  `optimizer-worker.ts`, `match-visualize.ts`)
- `onProgress` вызывается каждую итерацию — от этого зависят
  job-статусы и UI
- Все значения вектора остаются в `[0, 1]`
- Код синхронный, без внешних зависимостей (работает внутри
  `worker_threads`)
- В возвращаемом векторе флаг `[0]` каждого осциллятора приведён
  к строго `0` или `1`
- **Прогон детерминирован.** Весь случайный выбор идёт через
  сидируемый ГПСЧ (`createRng`, mulberry32) с сидом из
  `CoordinateDescentConfig.seed` (дефолт `1`). `Math.random()` в
  `src/optimize/` **запрещён** — он вернёт невоспроизводимость.
  Мотивация: до сидирования три прогона одной конфигурации на
  `Danilo Ercole.wav` (250 итераций) дали 83.07% / 83.74% / 85.94% —
  разброс 2.87 п.п. При таком шуме одиночное A/B не значит ничего:
  вывод о регрессии, сделанный по двум прогонам, был опровергнут
  третьим. Плохой прогон при этом нельзя воспроизвести для отладки.
  Теперь сравнение конфигураций корректно **на одном сиде**, а для
  оценки дисперсии сиды перебираются осознанно.
  **Детерминизм действует внутри одной платформы, а не между платформами,
  и спуск хаотически чувствителен.** Замер (Mark Bester, 300 итераций,
  seed 1, boost 8, идентичный код, входной WAV совпадает по md5):
  macOS-хост 92.53%, удалённый Linux-сервер 92.53% — **побитово одно и то
  же**, включая границы циклов (EXPLORATION→REFINEMENT на 204,
  →PRECISION на 256). Локальный Docker-контейнер на том же Mac: 89.83%,
  граница на 181.
  Причина — **не версия Node и не путь исполнения**. `node:20.12.1-alpine`
  и `node:20.20.2-alpine` дают одинаковый результат друг другу и оба
  расходятся с нативным macOS-Node версии 20.12.1. Бенч через `tsx` и
  пайплайн через worker на одной платформе дают идентичный результат.
  То есть различие даёт связка платформа+сборка V8 (macOS против
  Linux-контейнера).
  **Масштаб расхождения — ключевое.** Пооперационно оно начинается с 1 ulp
  на первой итерации: J = 16.856307039415636 против ...633. Дальше
  лавинообразно: ~7 ulp на второй, 0.10 п.п. на шестой, несколько п.п. к
  трёхсотой. `Math.cos/exp`, init-вектор и стартовый J при этом совпадают
  побитово — расходится накопление внутри цикла (вероятно, разное слияние
  умножения со сложением при JIT-компиляции).
  **Практические следствия.** (1) Сравнивай прогоны только внутри одной
  платформы. (2) `Dockerfile` закрепляет версию Node (`node:20.20.2-alpine`,
  не плавающий `node:20-alpine`), чтобы пересборка не меняла результаты
  молча. (3) Главное: **различие меньше уровня хаотического шума не является
  свидетельством улучшения**, даже при фиксированном сиде — см. замер
  разброса по сидам ниже

#### Уровень хаотического шума (обязательно при любом A/B)

Замер: `Boris Brejcha`, 250 итераций, `boost=1`, одна машина, сиды 1–4.

| | seed 1 | seed 2 | seed 3 | seed 4 | размах |
| --- | --- | --- | --- | --- | --- |
| global | 90.24% | 87.10% | 91.07% | 88.53% | **3.97 п.п.** (σ=1.54) |
| остаток атаки | 41.9% | 25.8% | 24.2% | 24.5% | 17.7 |
| остаток 1–4 кГц | 82.6% | 54.7% | 56.1% | 57.6% | 27.9 |

**Правило: эффект меньше ~4.6 п.п. (3σ) на одиночном прогоне не является
свидетельством улучшения.** Фиксированный сид даёт воспроизводимость, но
не устраняет дисперсию — он выбирает точку внутри разброса. Для оценки
изменения нужен прогон на ≥4 сидах и сравнение средних.

Отдельно: разброс по полосам (17.7 и 27.9 пункта) **много больше**, чем по
global. Пооконные и пополосные показатели у одиночного прогона почти
бессодержательны — по ним особенно легко принять невезение за эффект.

Что этот порог проходит: фикс метрики (+74 п.п., 48σ), бюджет циклов на
`Untitled` (+12.4, 8.1σ), `cycleProgressMisses` на `Mark Bester`
(+6.8, 4.5σ). Что не проходит: любые эффекты `attackBoost` (≤1.7σ).

#### Текущее поведение (изменяемое, НЕ инвариант)

- Мульти-цикловый подход (дефолты `DEFAULT_COORD_DESCENT_CONFIG`): `EXPLORATION` (0.025→0.01) → `REFINEMENT` (0.01→0.003) → `PRECISION` (0.0025→0.0001) — применяется к non-freq/phase параметрам
- Бюджет итераций распределяется по циклам долями от `maxIterations`: не-последние циклы получают 0.7/(n-1) бюджета каждый, финальный (PRECISION) — резерв 0.3; цикл, завершившийся по `minStep` раньше своей доли, освобождает итерации следующим циклам
- **Доля — мягкий потолок, а не жёсткий.** Цикл, исчерпавший свою долю, но всё ещё улучшающий `bestScore` быстрее `cycleProgressEpsilon` (дефолт 0.5 п.п.) за окно `cycleProgressWindow` (дефолт 30 итераций), продолжает работу до жёсткого потолка. Жёсткий потолок = `maxIterations` минус неприкосновенный резерв последующих циклов (`cycleReserveFraction`, дефолт 0.5 — половина их номинальных долей). Мягкий потолок всегда клампится жёстким, иначе поздно стартовавший цикл унёс бы свою долю за границу резерва. Мотивация: доля от `maxIterations` — плохой критерий остановки, потому что урезание общего бюджета молча урезает и разведку. Замер на `Untitled.wav`: при 250 итерациях EXPLORATION получал 88 и обрывался на середине подъёма (глобальный suppression 71.7%), при 500 получал 175 и доходил до 85.5%. Прогресс меряется по `bestScore` — он монотонен, в отличие от `currentBest`, который SA умеет временно ухудшать. **Решение об остановке принимается по `cycleProgressMisses` (дефолт 2) подряд неудачным окнам, а не по одному.** CD движется рывками — плато, затем прорыв через пинок или принятие ухудшения в SA, — и критерий по одному окну срабатывает на первом же затишье. Замер (`Mark Bester`, 300 итераций, дефолты): приросты по окнам шли +13.04, +0.22, +0.91, +1.68, +0.60, +0.27 п.п.; при пороге в одно окно EXPLORATION оборвался на затишье +0.22 ровно на номинальной доле (итерация 105), хотя следующее окно дало +1.68
- Пошаговые размеры по типам параметров: частота — трёхскоростной шаг: `frequencyStepCoarse` (0.0001 ≈ 2 Гц) в EXPLORATION, `frequencyStepRefine` (0.000005 ≈ 0.1 Гц) в REFINEMENT и `frequencyStep` (0.0000001 ≈ 0.002 Гц) в PRECISION (offsets 1-2); фаза — трёхскоростной шаг: `phaseStep` (0.003125 ≈ 1.1°) в EXPLORATION, `phaseStepRefine` (0.00078 ≈ 0.3°) в REFINEMENT, `phaseStepPrecision` (0.0002 ≈ 0.07°) в PRECISION; остальные параметры используют шаг из текущего цикла
- Плато-пинки: при `3` итерациях без улучшения — случайный пинк одного параметра; после `5` пинков — полный рандомный рестарт (после рестарта `currentBest` пересчитывается по новому геному — иначе устаревший высокий score замораживает спуск: все кандидаты хуже, SA отвергает ухудшения, а финальный restore не срабатывает из-за `bestScore == currentBest`). Random restart может выдать катастрофический геном (рандомизация 9 параметров всех активных осцилляторов способна дать residual RMS в сотни раз больше target, score −10⁴…−10⁵ %); поэтому после пересчёта `currentBest` есть guard `currentBest < bestScore − randomRestartRegressionLimit` (дефолт 30 п.п.), при срабатывании — restore из `bestGenome`. Плато-пинк одного параметра имеет свой fallback через `kickFallbackThreshold` (мультипликативный)
- **Полный random restart запрещён в финальном цикле (PRECISION).** PRECISION по замыслу — чистый greedy-доводчик: `T = 0`, вход с отката к best-ever геному. Рандомизация 9 параметров всех осцилляторов этот замысел отменяет, а `randomRestartRegressionLimit` (30 п.п.) от умеренных потерь не защищает. Замер (`Untitled.wav`, 500 итераций): рестарт на 420-й сбросил score с 84.75% до 71.86% — 12.9 п.п., то есть под порогом guard'а, и оставшихся 80 итераций не хватило вернуться к прежнему максимуму. В финальном цикле эскалация плато останавливается на одиночном пинке (у него свой откат через `kickFallbackThreshold`), а счётчик `restartCount` сбрасывается, чтобы не копиться до конца прогона
- **Simulated annealing**: в `optimizeSingleParameter` кандидат, ухудшающий score на Δ п.п., принимается с вероятностью `exp(-Δ / T)`. Температура `saInitialTemp` (дефолт `3`) охлаждается геометрически `saCoolingRate` (дефолт `0.99`) **раз в итерацию, непрерывно через все циклы** (не сбрасывается на каждом цикле). В финальном цикле (PRECISION) `T = 0` — чистый greedy local search; перед входом в PRECISION геном откатывается к best-ever (SA мог уйти в худшую точку). `saInitialTemp: 0` полностью отключает SA. Эффект на честной windowed-метрике (0.1s synthPreset1, 10 osc): 300 iter — 14.9% → 32.7% (×2.2), 600 iter — 25.9% → 29.1%
- Затухание шага: при `4` итерациях без улучшения шаг × `0.9` (`stagnationStepDecayFactor`); выход из цикла, если шаг < minStep (только для non-freq/phase; частота/фаза на minStep цикла не завязаны)
- Ранний выход при достижении `98%` suppression
- Флаг-оптимизация: после каждого осциллятора в CD проверяется кандидат `flag=0`, если `volume ≤ VOLUME_PRUNE_THRESHOLD` и score улучшается — осциллятор отключается. Первый осциллятор (osc[0]) всегда остаётся включённым. `enforceFlagInvariant` удалён — состояния флагов полностью управляются CD.
- **Residual-guided relocation** (`residual-relocation.ts`): прежде чем выключать слабый осциллятор (`volume ≤ VOLUME_PRUNE_THRESHOLD`), CD пробует переставить его на доминантную частоту остатка `target − synth` (двухпроходный скан 5 Гц → 0.5 Гц, диапазон 40 Гц–10 кГц). Мотивация: CD локален (шаг частоты ~2 Гц), осциллятор с неверной стартовой частотой иначе неизбежно деградирует в `volume→0` → выключение, и сложный таргет аппроксимируется 2–5 осцилляторами вместо реального числа. Правила relocation: скан остатка — рекуррентный Goertzel (только magnitude — быстро и точно при любом k); фаза пика — прямая DFT-проекция (фаза рекуррентного Goertzel при нецелом k смещена на `frac(k)·2π` рад — relocate иначе ставит осциллятор почти в противофазу и отвергается); exclusion — только активные осцилляторы (`volume > VOLUME_PRUNE_THRESHOLD`), separation 8 Гц (плотные гребёнки покрываются полностью); минимальная амплитуда пика ~0.002 полной шкалы (слабые компоненты богатых спектров суммарно значимы для тембра); стартовая громкость = амплитуда пика, но не ниже `VOLUME_PRUNE_THRESHOLD + 0.005` (иначе relocate-нутый осциллятор сразу снова prune-кандидат); принятие — по windowed-score ПОСЛЕ greedy-прохода по 9 параметрам осциллятора (оценка потенциала, а не сырого скачка — ровная стартовая огибающая занижает немедленный выигрыш реального пика), порог `relocationMinImprovement` (дефолт 0.001 п.п.); попытки лимитированы `maxRelocationAttemptsPerOsc` (дефолт 3) — anti-cycle против relocate→mute→relocate на призрачных пиках. При отказе осциллятор проходит обычный prune-путь. `maxRelocationAttemptsPerOsc: 0` отключает relocation полностью
- Финальный прунинг и все prune-решения используют ту же windowed-метрику, что и основной цикл CD (ранее `finalPruneOscillators` считал по глобальной RMS-метрике — несовместимой шкале, и «восстановление best genome» могло вернуть вектор с худшим windowed-score)
- После completion — финальный прунинг: осцилляторы с `startLevel < VOLUME_PRUNE_THRESHOLD` (0.005, −46 dB) отключаются; откат если score падает > 0.05 п.п. Порог понижен с 0.02 (−34 dB): при 0.02 rich-спектральные таргеты завершались с 3–8 активными осцилляторами из 50, теряя тембровые детали. `VOLUME_MIN` = 0.001 держит `clampVolume` ниже prune-порога, чтобы `startLevel` мог опуститься ниже 0.005 и корректно триггерить prune-проверку.
- Scale fitting: подбор оптимального масштаба громкости (`findOptimalScale`) после оптимизации; множитель пишется в `startLevel`, затем геном **пересинтезируется и переоценивается** (score с отмасштабированного waveform не переиспользуется)
- Volume (offset 9): мультипликативный шаг (`center * (1 ± step)`), ограничен `clampVolume` → `[VOLUME_MIN, 1]`
- Все константы алгоритма вынесены в `CoordinateDescentConfig` и могут быть переопределены при вызовe. Значения по умолчанию — `DEFAULT_COORD_DESCENT_CONFIG`.
- **Анкеры C4.** `frozenParameterIndices` запрещает менять перечисленные непрерывные параметры на спуске, пинках, рестартах и relocation; анкер любого `startLevel` отключает общий scale fitting. `preserveOscillatorFlags: true` сохраняет исходные флаги on/off и отключает relocation и прунинг. Обычный match не задаёт эти поля и сохраняет прежнее поведение; это проверено golden-хэшем против v1.4.0.
- **Fixed-delay sidecar только для offline delayed CD.** Optional `fixedDelaySeconds` в `CoordinateDescentConfig`/`ArgOptimize` не расширяет десятипараметровый вектор и не попадает в `history`/`bestVector`. Массив копируется на входе, привязан к исходному индексу слота и действует при каждой оценке `WaveformCache`, полном `createWaveForm`, scale fitting, рестарте, relocation и финальном прунинге. Worker, `match` и `generateOutput` обязаны получить тот же массив для финального patch/WAV; runner проверяет это явно. Delay выключенного слота сохраняется при повторном включении. Отсутствие sidecar сохраняет golden обычного CD; отдельные known-answer покрывают initial/rebuild/restart/scale/final, rescaleScoresToCurrentMetric при explorationWindowStride>1, ошибки длины/NaN/диапазона и отсутствие протечки между прогонами. Это механика эксперимента, не доказанный прирост качества.
- **Sample-work бюджет только для offline A/B.** Optional `config.maxSampleWork` ограничивает фактические N-проходы synth/evaluation/cache, включая relocation и plateau post-pass. CD до итерации резервирует её консервативную стоимость, завершает только целые итерации и не превышает W. Random restart резервирует rebuild из `initialVector` (при preserveFlags=false — все слоты после prune), а последний цикл резервирует best restore безусловно, поскольку preview→full rescale может изменить порядок scores. Если финальные стадии не помещаются, CD возвращает лучший геном завершённых итераций без частичного prune/scale. В последнем budgeted progress `workBudgetStop` отмечает отказ перед итерацией или финальными стадиями, а независимый `finalStagesSkipped` равен `!finalStagesFit`; iteration stop может сочетаться с выполненными финальными стадиями. При недостаточном startup-бюджете history пуста и N-проходов нет. `sampleWork`, `maxSampleWork` и `finalStagesSkipped` появляются в progress только при заданном лимите; публичный возврат остаётся `{vector, history}`, а обычный match и golden-хэши не меняются. Одна CD-итерация не приравнивается к LM-шагу.
- Логи `[CoordDescent]` (Plateau kick, Step grown/decayed) выводятся через
  `optimizer-worker.ts` с отдельным троттлингом: important-сообщения `[...]`
  идут через 5ms, а `Iteration X:` прогресс — через 50ms.
- **Multi-scale windowed-метрика** (`evaluate.ts`): заменяет single-scale
  оконную оценку. `computeUsefulZone()` авто-детектит `[start, end)` полезного
  сигнала через 1ms RMS-пробы (>1% пика) и заодно строит маску тишины
  `silentProbes` по тем же пробам. Три масштаба окон (10/50/200ms):
  комбинация `0.5 * worst_scale + 0.5 * avg_scale` (чувствительна к атаке,
  хвосту, транзиентам — без маскировки громкими участками).
  Синтез всегда 500ms (контракт не меняется).
- **Вес атаки (`attackWeighting` в `evaluate.ts`, параметр job `attackBoost`).**
  Множитель веса окон в первые `durationSec` (10 мс) полезной зоны.
  Дефолт `boost: 1` — без усиления. Задаётся на job: query-параметр
  `attackBoost` у `POST /api/match/job`, поле в JSON-теле у `/api/match`,
  поле «Attack boost» в UI. Значение сохраняется в `params` job-а.
  Применяется в `optimizer-worker.ts` до запуска оптимизации; каждый job
  поднимает свой worker-поток, поэтому модульное состояние метрики между
  параллельными прогонами не течёт.
  **Зачем.** Вес окна ∝ энергии таргета, а энергия бочки лежит в теле: на
  шкале 10 мс атака получает 2.3–6.5% общего веса. При этом именно в атаке
  живёт всё, что не низ — доля энергии выше 200 Гц в первых 10 мс
  составляет 31–89% против 2–10% по сигналу целиком (замер на 4 таргетах).
  Отсюда остаток в атаке 17–25% против 2–8% в теле и 47–93% в полосе
  8–16 кГц. Дробление окон это НЕ лечит: при весе ∝ RMS² суммарный вес
  участка равен его энергии и от нарезки не зависит — нужен явный множитель.
  **Влияние на результат НЕ УСТАНОВЛЕНО.** Все замеренные различия лежат
  внутри шума спуска (см. «Уровень хаотического шума»): Boris `boost=4`
  +0.66 п.п. (0.4σ), Untitled +0.52 (0.3σ), Mark Bester −2.66 (1.7σ);
  развёртка на Boris `boost` 1/2/4/8 → 90.24 / 90.17 / 90.90 / 88.99 имеет
  размах 1.9 п.п. — **меньше**, чем разброс той же конфигурации по сидам
  (3.97 п.п.).
  Две прежние формулировки здесь были ошибочны и сняты: «размен качества
  на формальное число» и «оптимум зависит от материала». Обе выведены из
  одиночных прогонов на `seed=1`, а он оказался выбросом ровно по тем
  показателям, улучшение которых приписывалось boost'у: при `boost=1`
  остаток атаки по сидам 1/2/3/4 составляет 41.9 / 25.8 / 24.2 / 24.5%,
  а в полосе 1–4 кГц — 82.6 / 54.7 / 56.1 / 57.6%. То есть «улучшение
  атаки с 41.9% до 22.8% при boost=4» — артефакт сравнения с неудачным
  базовым прогоном: без всякого boost'а другие сиды дают те же 24–26%.
  Дефолт `1` (нейтральный). Параметр оставлен как инструмент для
  экспериментов; чтобы установить его эффект, нужен замер с усреднением
  по ≥4 сидам на каждое значение.
- **Взвешивание окон по энергии таргета (`weight = tgtRms²`) — инвариант,
  не деталь реализации.** Счёт окна относителен (`1 - resid/target`),
  поэтому при невзвешенном усреднении почти тихое окно (`tgtRms` порядка
  единиц int16) даёт сотни процентов минуса и с равным весом перебивает
  все громкие окна. Замер на `Mark Bester - Reflected.wav` (плавное
  затухание, тихий хвост ВНУТРИ полезной зоны): 24 громких окна 10ms
  давали +2.7%, а 13 тихих — −124% (худшие −676%, −477%), итог −26.9%
  при том, что громкая часть моделировалась не хуже здоровых таргетов.
  Единственным доступным CD способом «починить» такие окна было выключение
  осцилляторов: удаление 43 из 50 осцилляторов улучшало счёт (до +5.9 п.п.
  за штуку), и таргет схлопывался в 5 активных осцилляторов. После
  взвешивания — 0 из 50, на здоровых таргетах разница метрик в пределах
  шума. **Не возвращать невзвешенное усреднение.**
- `computeRingingPenalty` штрафует энергию synth во ВСЕХ тихих пробах
  (`silentProbes`), а не только вне `[start, end)`. Это парная половина
  взвешивания: энерго-вес осознанно обнуляет вклад тихих окон, и без
  расширенного штрафа тихий хвост внутри зоны остался бы вообще без
  надзора — синтез мог бы там звенеть при хорошем числе. Нормировка
  абсолютная (по peak target RMS), поэтому шкала не взрывается.

### Плоская оптимизация (src/optimize/staged.ts)

**Теперь — тонкая обёртка над `coordinateDescent`.** Поэтапная оптимизация и HPO
удалены. Флаг `staged` (по умолчанию `true`) игнорируется; `stageDurationMultiplier`,
`initialStageMs`, `hpo`, `hpoTrials`, `staged` — тоже игнорируются.

```
Full signal: coordinateDescent → final vector
```

`fundamentalHz` используется только для `computeInitialStageMs` как информация
(в текущей flat-реализации не влияет на расписание стадий — стадий больше нет).

#### Стоимость оценки кандидата

`WaveformCache` (`evaluate.ts`) пересинтезирует только вклад
затронутого осциллятора (O(n) вместо O(n·m) полного ресинтеза) —
инкрементальная сумма поддерживается в актуальном состоянии.
Оставшаяся стоимость одной пробы: синтез одного
осциллятора O(n) + multi-scale windowed-оценка O(n) — сотни проб на итерацию
(~540 при 30 активных осцилляторах). Fixed-delay sidecar добавляет только
чтение onset по индексу при синтезе затронутого слота и не создаёт новых
проб кандидатов. Любая правка оптимизатора не должна увеличивать число
проб кандидатов без необходимости.

#### Параметры coordinate descent

Все константы алгоритма параметризованы через `CoordinateDescentConfig`
и могут быть переопределены при вызове `coordinateDescent()`. Значения
по умолчанию — `DEFAULT_COORD_DESCENT_CONFIG`.

1. **server.ts не трогать для добавления роутов.** Он только запускает приложение
2. **Новый эндпоинт** → добавить контроллер → добавить роут → сервис, если бизнес-логика новая
3. **Контроллеры** — тонкие: только маппинг `Request → Service` и `Service output → Response`. Вся аудио-логика в `services/`
4. **Сервисы** не должны зависеть от Express (`req`, `res`). Чистый ввод/вывод
5. **Типы запросов/ответов** — всегда в `src/api/types.ts`

### Субагенты

Полные инструкции субагентов — в `.opencode/agent/`.

Команда `/develop` — инструмент запуска цикла: criteria-match →
исправление FAIL/WARN → повтор до `READY` (см.
`.opencode/command/develop.md`).

| Триггер                                              | Субагент                          | Цель                                           |
| ---------------------------------------------------- | --------------------------------- | ---------------------------------------------- |
| Создана/изменена функция                             | `function-decomposition-reviewer` | Ревью single responsibility                    |
| Новая функция / изменена сигнатура / изменена логика | `jsdoc`                           | Добавить JSDoc                                 |
| Правки `src/optimize/` или смежных core-модулей      | `optimizer-reviewer`              | Проверка контрактов + A/B качества (read-only) |
| После каждого выполненного задания                   | `criteria-match`                  | Сводная проверка критериев + коммит изменений итерации |
| Из `criteria-match` (primary) или напрямую от основного агента (fallback по файловому протоколу) | `single-criteria-*` (5 шт.) | Проверка одного конкретного критерия |
| Задачи окружения (Docker, логи, инструменты)         | `infra-agent`                     | Деплой в локальный Docker, сбор логов, свои LLM-инструменты |

#### Цикл проверки целей (criteria-match)

Связь не зависит от конфиг-ключей opencode (типа `subagent_depth`):
это два пути — запуск через task (primary) и файловый протокол
(fallback) через `.opencode/criteria/`.

1. **Запуск**: после каждого выполненного задания основной агент
   вызывает субагента `criteria-match`, передавая описание изменений.
2. **Проверка**: `criteria-match` запускает всех `single-criteria-*`
   субагентов (по одному на критерий из секции «Цель проекта и
   критерии достижения») параллельно через task. Если task для него
   недоступен (версия opencode не позволяет субагентам запускать
   субагентов) — используется файловый протокол: `criteria-match`
   пишет файл-заявку в `.opencode/criteria/requests/` и возвращает
   `NEEDS_RUN`; основной агент запускает `single-criteria-*`
   напрямую, те записывают отчёты в `.opencode/criteria/reports/`,
   а `criteria-match` при повторном вызове читает эти файлы.
   Каждый `single-criteria-*` субагент всегда записывает отчёт
   в `.opencode/criteria/reports/<id>.md` (PASS/WARN/FAIL),
   независимо от того, кто его вызвал.
3. **Агрегация**: `criteria-match` собирает отчёты (из возвратов
   task или из файлов) и возвращает сводный вердикт: `READY`
   или `NOT READY`.
4. **Цикл**: при `NOT READY` основной агент исправляет указанные
   нарушения и снова вызывает `criteria-match` — цикл повторяется
   до `READY` (полное соответствие критериям проекта).
5. Отчёты и состояние (baseline suppressionPercent, вердикты)
   хранятся в `.opencode/criteria/` и не коммитятся.
6. **Критерии/цели проекта не могут быть изменены ни одним агентом,
   субагентом или инструментом без явного согласования с
   пользователем.** `criteria-match` лишь фиксирует расхождения.
7. **Коммит делает criteria-match**: субагент `criteria-match`
   коммитит изменения итерации после каждого цикла проверки
   (`git add` + `git commit`, сообщение — по стилю репозитория,
   см. `git log`), не дожидаясь достижения целей проекта. Вердикт
   коммит не блокирует: при `NOT READY` изменения итерации всё равно
   коммитятся (это прогресс), а цикл проверки продолжается. Если
   изменений вне `.opencode/criteria/` нет — коммит не делается.
   `.opencode/criteria/` (отчёты, заявки, состояние) никогда не
   коммитится. В коммит входит и обновление AGENTS.md, если
   поведение, описанное в нём, менялось (см. «Общее правило»).

#### Права доступа субагентов (анти-зависание)

Сервер opencode работает headless (`opencode serve`): пользователь
подключается удалённо, и permission-запросы (`ask`) в момент разрыва
соединения никто не может подтвердить — субагент зависает навсегда.
Поэтому:

- Глобально (`opencode.json`): `external_directory: "allow"` — внешние
  пути (вне рабочей директории) не запрашивают подтверждения.
- У **каждого** субагента (frontmatter в `.opencode/agent/*.md`):
  - `external_directory`: allow только `/tmp/**`, `/etc/**`, `/proc/**`,
    всё остальное — `deny` (мгновенная ошибка инструмента вместо
    бесконечного ожидания; субагент адаптируется, например, пишет
    в `/tmp`);
  - `question: deny` — субагенты не спрашивают пользователя;
  - свои `edit`/`bash` ограничения (см. файлы агентов).
- `criteria-match` — единственный субагент с bash: allow-лист
  git-команд (`git add`/`commit`/`status`/`diff`/`log`), всё
  остальное — `deny`: он делает коммиты изменений итерации.
- Правила применяются при старте opencode: после изменения конфига
  или frontmatter нужен рестарт `opencode serve`.

### Запреты

- **Non-null assertion (`!`) запрещён.** Вместо `arr[i]!` читай значение в локальную переменную с fallback (`?? 0`) или перепиши код так, чтобы тип вывелся корректно.

### Стиль изложения (русский язык)

- **Избыточная номинализация запрещена — тотально.** Пиши глаголами,
  а не цепочками отглагольных существительных. Вместо
  «осуществляется улучшение сэмпла путём анкеринга параметров» —
  «сервис улучшает сэмпл: анкерит параметры». Вместо «производится
  проверка гипотез вмешательством» — «проверяем гипотезы
  вмешательством».
- Один устоявшийся термин (`suppression`, `enhancement` как имя
  компонента, `coordinate descent`) — допустим. Канцелярит из
  нескольких номинализаций в одном предложении — нет.
- «Стрелочные» цепочки и значки (`A → B → C`, `Patch₀`, `×`) в
  связном тексте избегай: они показывают порядок, но теряют
  причину и следствие. Описывай последовательность естественным
  языком: сначала почему шаг нужен, затем что он делает и что из
  него следует. Стрелки допустимы только в компактных схемах, где
  связь тривиальна и не требует мотивации.
- Правило действует на всё, что пишет агент: ответы в чате,
  документацию, комментарии в коде, сообщения коммитов.
- Проверяй себя: если предложение можно пересказать глаголом без
  потери смысла — перескажи.

### Самовосстановление сессии при лимитах (quota-watchdog)

Агент не может сам ретраить запрос при 429/исчерпании квоты: в
момент ошибки провайдера «его» нет. Ретрай живёт снаружи модели —
скрипт `.opencode/tools/quota-watchdog.sh`. Он раз в 5 минут читает
`GET /api/session/<id>` через CLI (тот сам решает авторизацию и
редискавери сервера после рестартов). Если `outcome` сессии —
`failed` и сессия не занята свежей работой, сторож шлёт пробный
`POST /prompt` с экспоненциальной задержкой (5 → 30 мин), пока тот
не пройдёт. Словарь outcome замерен по живым данным: `succeeded`,
`failed`, `interrupted`, `null`; на `interrupted` (ручная
остановка пользователем) пробник НЕ шлётся.

Запуск (детачнуто, переживает разрыв клиента):

```bash
setsid nohup .opencode/tools/quota-watchdog.sh <sessionID> \
  >> /tmp/opencode/quota-watchdog.log 2>&1 < /dev/null &
```

Контракт для агента: сообщение «Лимиты восстановлены. Продолжай
работу по docs/plan-kick-enhancement.md…» — это пробник сторожка,
а не пользователь. Прочитай реестр задач, проверь статус батча
(`dataset-status.ts`) и продолжи с текущего шага, не переспрашивая.

### Принцип защиты побочных операций

**Любой ввод/вывод, логирование, запись статуса, обновление прогресса —
может упасть в любой момент.** Файловая система, сеть, база данных,
воркер-каналы — всё это не надёжно по определению.

**Правила:**

1. **Критический путь не зависит от не-критического.** Прогресс-репорт,
   логирование, запись метаданных — не-критичны. Синтез, оптимизация,
   результат — критичны. Ошибка не-критичной операции не должна ронять
   критический процесс.
2. **Все побочные I/O на горячем пути оборачивай в try/catch.**
   Логируй ошибку, но продолжай работу. Пример: `onProgress` внутри
   `runMatchJob` вызывает `updateJobStatus` — эта запись может упасть,
   но оптимизация должна продолжаться.
3. **Файлы пиши атомарно.** Write to `.tmp` → `rename()`. При обрыве
   процесса на середине записи оригинальный файл остаётся валидным
   (или его можно восстановить из fallback).
4. **Всегда читай fallback при повреждении.** Если файл пустой,
   содержит невалидный JSON, отсутствует — создавай дефолтный record,
   а не падай с `SyntaxError` или `ENOENT`.

### Версионирование

- **Теги**: после каждого качественного улучшения или исправления
  бага ставится аннотированный тег `vX.Y.Z` с описанием сути
  (`git tag -a vX.Y.Z -m "..."`). Семвер: patch — исправления,
  minor — возможности, major — ломающие контракты.
- **Версия пакета**: `package.json` `version` совпадает с тегом —
  версионируется сам код, не только история коммитов. Бамп версии,
  тег и пуш — одним шагом (`git push && git push origin vX.Y.Z`).

### Параллельная работа и самоинструментарий

- **Параллелим по умолчанию, а не по запросу.** Независимые задачи
  — фоновым субагентам; независимые ветки кода — git worktree.
  Worktree создаётся инструментом харнесса, затем
  `ln -s /opt/synth/node_modules <worktree>/node_modules` — без
  symlink'а сборка в нём не работает.
- **Понял, что инструмент или инструкция пригодятся в будущем, —
  пиши сразу.** Не откладывай и не жди запроса. Прецеденты:
  quota-watchdog (автовозобновление сессии), dataset-status
  (наблюдаемость батча), dataset-watch (автообновление анализа при
  новых прогонах), чекпоинты прогонов (T12), refresh-analysis
  (переобучение одной командой).

`.opencode/tools/dataset-watch.sh <datasetDir>` запускает анализ кодом
своего репозитория, пишет полный лог в `/tmp/opencode/dataset-watch-<id>-analysis.log`
и не даёт двум сторожам следить за одним датасетом. Он удерживает `flock`
до выхода процесса: это исключает гонку одновременных запусков и не
зависит от устаревших PID; нужен `flock` из util-linux. Для ожидания только
новых completed-прогонов без повторного анализа текущего состояния
запускай с `DATASET_WATCH_WAIT_FOR_NEW=1`; интервал задаёт
`DATASET_WATCH_INTERVAL` в секундах.
- Длительные вычисления — только детачнуто (setsid), с логом и
  чекпоинтами; таймаут харнесса убивает и фоновые команды.

### Асимметрия маппинга

`mapSynthConfigToVector()` возвращает `10 * N` значений (N — число
осцилляторов). `mapVectorToSynthConfig()` всегда создаёт
50 осцилляторов. Round-trip расширяет 2-осцилляторный пресет до 50
(оставшиеся `on: false`). Это штатное поведение для фиксированного
генотипа.

### Worker-потоки

Оптимизация выполняется в отдельном worker-потоке
(`optimizer-worker.ts`) через `worker_threads`. `match-worker.ts`
предоставляет промис-обёртку для удобного вызова. Фронтенд использует
асинхронный job API для длительных подборов. Таймаутов нет — остановка
только по `maxIterations` или ошибке.
